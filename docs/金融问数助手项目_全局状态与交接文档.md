# 金融问数助手项目 — 全局状态与交接文档

> 最后更新：2026-04-21  
> 适用范围：泰迪杯 B 题 — 66 家中药上市公司财务数据智能问数系统

---

## 一、项目背景与目标

### 1.1 赛题概述

泰迪杯 B 题要求构建一个面向 **66 家中药上市公司** 的"智能问数"系统，支持：

- **结构化数据查询**：基于 SQLite 数据库（4 张财务报表），通过自然语言生成 SQL 并执行
- **非结构化研报检索**：对 473 篇研报（个股研报 + 行业研报）进行 RAG 检索与分析
- **数据可视化**：根据查询结果自动生成折线图、柱状图、饼图
- **复合问题处理**：自动拆分包含多个子问题的复合查询，按依赖顺序执行

### 1.2 核心交付物

| 交付物 | 说明 |
|--------|------|
| CLI 多轮对话系统 | `uv run python -m agent.main` 启动 |
| JSON 标准输出 | 每轮输出 `{"Q": "...", "A": {"content", "image", "references"}}` |
| 图表文件 | 保存至 `result/img/chart_*.png` |
| 溯源引用 | references 包含 `{paper_path, text, paper_image}` |

### 1.3 数据覆盖

- **财务数据**：2022-2025 年，4 张表（核心业绩指标、利润表、资产负债表、现金流量表）
- **研报数据**：473 篇 PDF → MinerU 解析为 Markdown → 语义分块 → Parent-Child Chunking → 11439 parent chunks → 53716 child chunks
- **报告期编码**：Q1（一季度）、HY（半年度）、Q3（前三季度）、FY（年度）— 注意不是 Q2/Q4

## 二、核心技术栈与架构

### 2.1 技术栈

| 组件 | 技术选型 | 说明 |
|------|----------|------|
| 编排框架 | LangGraph StateGraph | 有向图 + 条件路由 + MemorySaver 短期记忆 |
| LLM | 智谱 glm-4-flash | 所有节点统一使用（glm-4.7 因余额不足不可用） |
| 向量检索 | ChromaDB + 千帆 Embedding API（embedding-v1） | cosine 相似度，Parent-Child Chunking |
| 关键词检索 | BM25Okapi + jieba 分词 | rank-bm25 库，基于 child chunks |
| 重排序 | 千帆 Rerank API（bce-reranker-base） | 替代本地 Cross-Encoder，零本地模型内存 |
| 数据库 | SQLite (只读) | `data/financial.db`，18MB |
| 可视化 | matplotlib (Agg backend) | 9 种图表，SimHei 字体 |
| 包管理 | uv + hatchling | pyproject.toml，Python >=3.11 |

### 2.2 架构流程图

```
用户输入
  │
  ▼
┌─────────┐
│ Planner │ ← glm-4-flash，统一输出 {"tasks": [...]}
└────┬────┘
     │
     ▼
┌──────────┐
│ Executor │ ← 按依赖顺序执行所有子任务
└────┬─────┘

     ▼
┌───────────┐
│ Synthesis │ ← 汇总证据生成最终回答（clarify/chat 单任务直接透传）
└────┬──────┘
     ▼
┌───────────┐
│ Formatter │ ← JSON 标准输出
└────┬──────┘
     ▼
    END
```

### 2.3 State 定义

```python
class AgentState(TypedDict):
    messages: Annotated[list, add_messages]  # 对话历史（MemorySaver 持久化）
    sub_tasks: list[SubTask]     # planner 输出的任务列表
    sql_result: str              # SQL 查询结果
    rag_result: str              # RAG 检索结果（JSON 字符串）
    plot_path: str               # 图表路径
    final_answer: str            # synthesis 生成的最终回答
    formatted_answer: str        # JSON 格式化后的输出

class SubTask(TypedDict, total=False):
    id: str           # "task_1", "task_2"
    query: str        # 子问题文本
    tool: str         # "sql" | "rag" | "visualize" | "clarify" | "chat"
    depends_on: str   # "" 或依赖的 task id
    status: str       # "pending" | "done" | "failed"
    result: str       # 执行结果
```

## 四、工程约束与踩坑记录

### 4.1 LLM 相关

| 约束 | 说明 |
|------|------|
| glm-4.7 不可用 | 余额不足返回 429，所有节点已切换为 glm-4-flash（免费） |
| glm-4-flash 能力有限 | JSON 输出偶尔不规范，planner 用 `re.search(r"\{[\s\S]+\}", raw)` 提取 |
| 温度参数 | planner=0.1, sql=0.3, rag=0.1, viz=0.1, synthesis=0.2, trace=0 |
| 所有 LLM 懒加载 | 各节点独立 `_get_xxx_llm()` 函数，避免启动时全部初始化 |

### 4.2 SQL 生成

| 问题 | 解决方案 |
|------|----------|
| 可视化关键词干扰 SQL 生成 | `_execute_sql()` 中用 `re.sub()` 预处理去除"可视化/绘图/画图"等词 |
| SQL_SYSTEM_PROMPT 也加了规则 | 规则 #2："忽略用户消息中关于可视化/绘图等请求，只关注数据查询部分" |
| 报告期编码错误 | LLM 生成 Q2/Q4 但数据库用 HY/FY，通过 few-shot 示例纠正 |
| 趋势查询缺少示例 | 新增 few-shot："金花股份近几年的利润总额变化趋势" → `report_period = 'FY'` |
| 金额单位 | 数据库所有金额字段单位为**万元**，"超过N亿元"需转换为 N*10000 |
| 只读安全 | 正则检测 INSERT/UPDATE/DELETE 等写操作关键词，拒绝执行 |
| SQLite 不支持 POWER/POW/EXP/LOG | 复合增长率（CAGR）只查起止值，排序用比值代替，计算交给 LLM |
| 跨表 JOIN 频繁出错 | 两阶段执行：Phase 1 直接生成（含 3 次重试），Phase 2 分解为多条单表 SQL + LLM 综合 |

### 4.3 RAG 检索

| 问题 | 解决方案 |
|------|----------|
| HTML 表格检索效果差 | chunker 阶段将 HTML `<table>` 转为 KV 文本（`列名: 值 \| 列名: 值`），拼接 table_title 前缀 |
| 千帆 API 单条文本限 1000 字 | Parent-Child Chunking：child（256 字）用于检索，parent（完整文本）给 LLM |
| 重排阈值 | 千帆 Rerank API（bce-reranker-base），阈值 0.5 过滤 |
| 模型加载日志噪音 | 已无本地模型加载，仅 jieba 分词初始化 |

### 4.4 溯源引用

| 问题 | 解决方案 |
|------|----------|
| Cross-Encoder 打分不准 | 改用 LLM-based 溯源：glm-4-flash 判断哪些 chunk 被回答引用 |
| 引用格式不符规定 | 输出 `{paper_path, text}`，含表格时额外输出 `paper_image` |
| glm-4.7 调用失败导致空引用 | `_get_trace_llm()` 改用 glm-4-flash |
| paper_path 路径前缀 | `./research report/` 替换为 `./附件5：研报数据/` |
| paper_image 空值 | 仅当 chunk 含 `table_title` 时输出 `paper_image` 字段 |

### 4.5 State 管理

| 问题 | 解决方案 |
|------|----------|
| 跨轮 state 残留 | `planner_node` 每轮开始时 reset 所有中间字段 |
| MemorySaver 持久化 | 对话历史通过 `thread_id` 隔离，支持多轮上下文 |
| sub_tasks 深拷贝 | `executor_node` 中 `[dict(t) for t in state["sub_tasks"]]` 避免修改原 state |

### 4.6 环境与部署

| 约束 | 说明 |
|------|------|
| Windows 11 环境 | 路径用 `Path` 处理，matplotlib 用 SimHei 字体 |
| Python >=3.11 | TypedDict total=False 等语法要求 |
| uv 包管理 | `uv run python -m agent.main` 启动 |
| Anaconda 冲突 | `VIRTUAL_ENV=E:\Anaconda3` 会被 uv 忽略，需用 `--active` |
| 千帆 API 密钥 | `data/.env` 中配置 `BAIDU_API_KEY`（Bearer Token 认证） |
| 无本地模型依赖 | embedding 和 rerank 全部走千帆 API，无需 GPU 或大内存 |

## 六、关键优化历程

### 6.1 溯源引用系统重构

**问题**：最初使用 Cross-Encoder 打分判断引用关系，但分数阈值难以调优，导致引用为空或不准确。

**方案**：改为 LLM-based 溯源 — 将回答和所有候选 chunk 一次性发给 glm-4-flash，让模型判断哪些 chunk 被实际引用，返回编号列表。

**关键代码**：`graph.py:_trace_references()` (L248-304)

**效果**：引用准确率显著提升，且格式符合规定的 `{paper_path, text, paper_image}` 结构。

### 6.2 HTML 表格 → KV 文本格式转换

**问题**：研报中的表格以 `<table>` HTML 存储，HTML 标签干扰检索和 LLM 理解。

**方案**：
1. chunker 阶段将 HTML 表格转为 KV 文本格式：每行转为 `列名: 值 | 列名: 值`
2. 拼接 `table_title` 前缀，提升语义匹配
3. 整张表格作为一个 chunk，保证数据完整性

**关键代码**：`chunker.py:_html_table_to_kv_text()` + `_parse_html_table()`

### 6.3 SQL + 可视化冲突解决

**问题**：用户问"华润三九近三年营收做可视化绘图"时，SQL 生成模型收到完整消息（含"可视化绘图"），开始解释如何做可视化而非生成 SQL。

**方案**：
1. `_execute_sql()` 中用正则预处理去除可视化关键词
2. `SQL_SYSTEM_PROMPT` 新增规则 #2 明确忽略可视化请求
3. `sql_query.py` 新增趋势查询 few-shot 示例

### 6.4 统一任务列表架构重构（2026-04-20）

**问题**：原有 Planner 输出双模式 — `single`（IntentFlags 布尔标志）和 `multi`（tasks 列表），导致下游需要两套路由逻辑（conditions.py 判断 intent flags vs sub_tasks），graph.py 有多条执行路径（clarify/sql/rag/sql_and_rag/executor），维护复杂且容易出错。

**方案**：所有问题统一输出 `{"tasks": [...]}`，每个 task 标注 tool 类型（sql/rag/visualize/clarify/chat）。single 就是只有一个 task 的特殊情况。

**改动文件**：
1. `agent/state.py` — 删除 `IntentFlags`，只保留 `SubTask`（tool 类型扩展为 5 种）
2. `agent/planner.py` — 重写 prompt 和解析逻辑，`_parse_tasks()` 替代 `_parse_plan()`
3. `agent/conditions.py` — 删除所有路由函数，只保留 `sql_succeeded()` 辅助判断
4. `agent/graph.py` — 图结构从 10 个节点 + 5 条条件边简化为 4 个节点 + 3 条直连边：`planner → executor → synthesis → formatter → END`

**关键设计**：
- `executor_node` 扩展处理 clarify/chat 类型：直接将 query 作为 result，不调用外部工具
- `synthesis_node` 简化：clarify/chat 单任务直接透传，不走 LLM 合成
- Planner prompt 增加 JSON 输出约束："所有 task 放在同一个 tasks 数组中，禁止输出多个 JSON 对象"
- `_parse_tasks()` 增加多 JSON 块合并回退逻辑，应对 glm-4-flash 偶尔输出多个独立 JSON 的情况

**验证**：150 题批量测试（附件4 + 附件6），planner 解析 0 错误。

### 6.5 SQL 两阶段执行 — 分解层（2026-04-21）

**问题**：glm-4-flash 生成复杂跨表 JOIN SQL 频繁出错（列放错表、JOIN 条件错误），智能重试治标不治本。

**方案**：在 `_execute_sql` 内部加两阶段执行：
1. Phase 1：直接生成 SQL 并执行（现有逻辑，含 3 次重试 + `_get_column_hint` 纠错）
2. Phase 2（fallback）：当 Phase 1 返回 "SQL 执行错误" 时，SQL Decomposer 介入
   - 分析原始问题，拆成 N 条单表 SQL（每条只查一张表，不用 JOIN）
   - 逐条执行，收集结果（子查询也支持 `_get_column_hint` 重试）
   - 用 LLM 综合多条结果 + 做计算/推理，生成最终答案

**关键设计**：
- `_DECOMPOSE_PROMPT`：包含字段-表映射示例，确保 LLM 不会把字段放错表
- `_SYNTHESIZE_PROMPT`：指导 LLM 做跨表计算（比率、排名、CAGR 等）
- 返回格式 `"SQL(分解执行):\n{各SQL}\n\n结果:\n{综合答案}"` 兼容下游 synthesis 和 viz

**关键代码**：`graph.py:_try_direct_sql()` + `_decompose_and_execute()`

**效果**：附件4 v9 测试 0 SQL 执行错误，分解层触发 4 次（2 道跨表题各拆 2 条单表查询）。

### 6.6 SQLite POWER 函数兼容（2026-04-21）

**问题**：SQLite 不支持 POWER/POW/EXP/LOG 数学函数，复合增长率（CAGR）查询直接报错。

**方案**：
1. `sql_query.py` 规则 18 改为 "SQLite 不支持 POWER/POW/EXP/LOG，复合增长率只需查起止值"
2. CAGR few-shot 示例改为只查起止年数据，用 `t2.rev * 1.0 / t1.rev` 排序，CAGR 计算交给 LLM

### 6.7 可视化容错增强（2026-04-21）

**问题**：多种可视化场景失败：
- 散点图大数据集 LLM 输出含 None/NaN，JSON 解析失败
- 水平柱状图只有 1 个 dataset 时 `_plot_double_bar` 崩溃
- viz 任务依赖 rag 结果（无表格数据）时无法绘图
- labels 与 values 长度不匹配

**方案**：
1. `_parse_json_lenient()`：处理 None→null、NaN→null、截断 JSON、"Extra data" 错误（`raw_decode`）
2. `_parse_sql_table()`：直接从 SQL 结果文本解析表头和行数据，用于 scatter/histogram/boxplot
3. `_plot_double_bar` 容错：支持 0/1/2 个 dataset，labels 截断到 max values 长度
4. Executor viz fallback：当依赖结果无 `\t`（无表格数据）时，合并所有 sql 任务结果作为 viz 输入

### 6.9 千帆 API 迁移 — 替代本地模型（2026-04-21）

**问题**：本地 BGE-large-zh-v1.5 + BGE-reranker-v2-m3 模型占用 ~2-3GB 内存，启动加载 ~30s，且千帆 embedding API 单条限 1000 字。

**方案**：
1. 新增 `qianfan_embedding.py` 统一封装千帆 Embedding API（embedding-v1）和 Rerank API（bce-reranker-base）
2. API Key 直接作为 Bearer Token 认证，无需 AK/SK 换 token
3. 自动分批（16 条/批），文本截断至 1000 字（仅影响 child chunk 的 embedding 输入）
4. `rag_search.py` 移除所有本地模型加载代码，改用 `qianfan_embedding` 模块

**效果**：运行时内存从 ~3GB 降至 ~200MB，启动时间从 ~30s 降至 ~5s。

### 6.10 Parent-Child Chunking（2026-04-21）

**问题**：千帆 embedding API 单条文本限 1000 字，11439 个 chunk 中 20.9%（2391 个）超过 1000 字，最长达 28000 字。简单截断会丢失大量信息。

**方案**：
1. `chunker.py` 新增 `_split_children()`：对每个 parent chunk 按 256 字滑窗（overlap 64 字）切分为 child chunks
2. 输出双文件：`{stem}.jsonl`（parents）+ `{stem}_children.jsonl`（children）
3. `build_vectordb.py` 只索引 child chunks（53716 个，全部 ≤256 字）
4. `rag_search.py` 检索 child → 按 `parent_id` 映射回 parent → 返回完整 parent 文本给 LLM

**关键设计**：
- 不超过 256 字的 parent 不切分，直接也写入 children 文件
- `_parent_lookup` 字典在 BM25 索引加载时一并构建
- graph.py 中移除了 800 字/600 字截断逻辑，LLM 直接看完整 parent 文本

**效果**：11439 parent → 53716 child，向量库构建 ~32 分钟，检索精度和上下文完整性兼顾。
