# 金融问数助手 — 技术简报

> 供撰写技术报告参考 | 2026-04-21

---

## 1. 系统概述

本系统是面向 66 家中药上市公司的"智能问数"平台，基于 LangGraph 有向图编排框架构建，集成结构化数据查询（Text-to-SQL）、非结构化研报检索（RAG）和数据可视化三大能力。系统采用统一任务列表架构，通过意图规划器（Planner）将所有问题统一拆解为任务列表，由 Executor 按依赖顺序执行，Synthesis 汇总生成最终回答。

## 2. 核心技术方案

### 2.1 意图规划与任务编排

采用 LLM-based Planner 进行意图解析，统一输出任务列表 `{"tasks": [...]}`：

- 每个 task 指定工具类型（sql / rag / visualize / clarify / chat）和依赖关系（depends_on）
- 单一问题输出 1 个 task，复合问题输出多个 task，格式完全统一
- clarify（缺少年份等关键信息时触发澄清）和 chat（元问题直接回答）作为 task 类型处理，无需额外路由分支
- Executor 节点按依赖顺序执行所有 task，clarify/chat 类型直接将 query 作为 result 透传

图结构简化为 4 个节点的线性流程：`Planner → Executor → Synthesis → Formatter → END`

### 2.2 Text-to-SQL（两阶段执行）

- 使用 glm-4-flash 模型，基于详细的 DB Schema 描述和 12 类 few-shot 示例生成 SQL
- 覆盖：基础查询、条件筛选、Top N 排名、多表 JOIN、行业均值对比、计算字段、跨期趋势、复合增长率（CAGR）、交集查询等
- 安全机制：正则检测写操作关键词，仅允许 SELECT；SQLite 以 `mode=ro` 只读连接
- 启发式回退：当 LLM 生成失败时，基于关键词映射表 `_METRIC_MAP` 构建简单 SQL
- SQLite 兼容：不使用 POWER/POW/EXP/LOG 函数，CAGR 只查起止值由 LLM 计算

两阶段执行策略：
1. **Phase 1 — 直接生成**：LLM 生成 SQL → 执行 → 失败时最多重试 3 次（`_get_column_hint` 提供列名纠错提示）
2. **Phase 2 — 分解回退**：当 Phase 1 返回 SQL 执行错误（尤其是跨表 JOIN 错误）时，SQL Decomposer 介入：
   - 将问题拆成 N 条单表 SQL（每条只查一张表，不用 JOIN）
   - 逐条执行并收集结果（子查询也支持列名纠错重试）
   - LLM Synthesizer 综合多条结果进行计算/推理，生成最终答案

### 2.3 RAG 混合检索（Parent-Child Chunking）

采用 Parent-Child Chunking 架构：child chunk（256 字滑窗，overlap 64 字）用于精确检索，命中后返回对应的 parent chunk（完整语义分块）给 LLM，兼顾检索精度和上下文完整性。

四阶段流程：

1. **双路召回**：千帆 Embedding API（embedding-v1）向量检索（ChromaDB，top 20）+ BM25 关键词检索（jieba 分词，top 20），均基于 child chunks
2. **合并去重**：按 child chunk ID 去重
3. **千帆 Rerank API 重排**：bce-reranker-base 打分，阈值 0.5 过滤，取 top 5
4. **Parent 映射**：将命中的 child chunk 按 `parent_id` 映射回 parent chunk，多个 child 命中同一 parent 只保留最高分，最终返回完整 parent 文本给 LLM

表格增强：
- 入库时将 HTML `<table>` 转为 KV 文本格式（`列名: 值 | 列名: 值`），拼接 `table_title` 前缀，提升语义匹配
- RAG prompt 包含表格格式说明和完整提取规则

### 2.4 LLM-based 溯源引用

将生成的回答和所有候选 chunk 一次性发送给 glm-4-flash，由模型判断哪些 chunk 被实际引用，返回编号列表。相比 Cross-Encoder 打分方案，语义理解更准确，避免了阈值调优问题。

输出格式：`{"paper_path": "研报PDF路径", "text": "引用片段摘要"}`，当 chunk 含 `table_title` 时额外输出 `"paper_image": "表格标题"`

### 2.5 数据可视化

- LLM 根据用户问题和 SQL 结果决定图表类型和数据组织
- 支持 9 种图表：折线图、柱状图、饼图、雷达图、直方图、双条形图、散点图、表格、箱线图
- matplotlib Agg 后端渲染，支持单系列和多系列数据
- 图表保存为 PNG，路径写入 state 供 formatter 输出
- 容错机制：JSON 宽松解析（处理 None/NaN/截断）、直接从 SQL 结果解析散点/直方/箱线数据、labels/values 长度自动对齐
- Executor fallback：当 viz 依赖的结果无表格数据时，自动合并所有 sql 任务结果作为输入

### 2.6 任务执行引擎

Executor 节点统一处理所有任务类型：
- sql → `_execute_sql()`：两阶段执行 — Phase 1 直接生成（含 3 次重试），Phase 2 分解为单表查询 + LLM 综合
- rag → `_execute_rag()`：混合检索 + LLM 生成 + 溯源引用
- visualize → `_execute_viz()`：依赖 sql 结果，LLM 决定图表类型并渲染
- clarify / chat → 直接将 query 作为 result，不调用外部工具
- 通过 `depends_on` 字段实现依赖传递（如 visualize 依赖 sql 的结果）
- Synthesis 节点：多任务时按子任务组织证据生成综合回答；clarify/chat 单任务直接透传不走 LLM

## 3. 数据处理管线

### 3.1 财务报表处理

```
PDF → MinerU 解析 → Markdown → merged_financial_parser.py → SQLite
```

- 解析 66 家公司 × 4 年 × 4 报告期的财务报表
- 表格识别、字段别名映射、跨表数据补充、质量校验
- 最终生成 4 张规范化表，约 2300 行数据

### 3.2 研报处理

```
PDF → MinerU 解析 → Markdown → preprocess.py 清洗 → chunker.py 分块 → Parent JSONL + Children JSONL
                                                                        ↓
                                                              build_vectordb.py → ChromaDB（仅索引 children）
```

- 473 篇研报（个股 + 行业），清洗后按标题层级 + 表格边界语义分块
- HTML 表格转为 KV 文本格式（`列名: 值 | 列名: 值`），拼接 `table_title` 前缀
- Parent-Child Chunking：parent chunk 保留完整语义分块文本，child chunk 按 256 字滑窗（overlap 64 字）切分
- 千帆 Embedding API（embedding-v1）编码 child chunks，11439 个 parent → 53716 个 child 入库，耗时约 32 分钟

## 4. 输出格式规范

每轮对话输出标准 JSON：

```json
{
  "Q": "用户问题原文",
  "A": {
    "content": "回答正文（换行符替换为分号）",
    "image": ["result/img/B2001_1.png"],
    "references": [
      {
        "paper_path": "./附件5：研报数据/xxx.pdf",
        "text": "引用的研报片段摘要",
        "paper_image": "表格标题（仅当引用含表格时出现）"
      }
    ]
  }
}
```

- `image` 和 `references` 仅在有值时出现
- `paper_image` 仅当引用 chunk 含 `table_title` 时输出
- `content` 中的 `\n\n` 和 `\n` 替换为中文分号 `；`
- 图表以 `问题编号_顺序编号.png` 命名（如 B2001_1.png）

## 5. 关键设计决策

| 决策 | 理由 |
|------|------|
| 统一任务列表架构 | 消除 single/multi 双模式，4 节点线性流程，维护简单 |
| 所有节点用 glm-4-flash | glm-4.7 余额不足，glm-4-flash 免费且速度快 |
| SQL 两阶段执行 | 直接生成 + 分解回退，解决跨表 JOIN 频繁出错问题 |
| SQLite 不用 POWER 函数 | CAGR 只查起止值排序，计算交给 LLM |
| LLM 溯源替代 Cross-Encoder 打分 | 语义理解更准确，无需调阈值 |
| HTML 表格转 KV 文本 | `列名: 值` 格式比 HTML 标签更利于检索和 LLM 理解 |
| Parent-Child Chunking | child（256 字）用于检索适配 API 限制，parent（完整文本）给 LLM 保证上下文完整 |
| 千帆 API 替代本地模型 | 零本地模型内存，embedding-v1 + bce-reranker-base，运行时内存从 ~3GB 降至 ~200MB |
| Planner 每轮 reset state | 防止 MemorySaver 导致跨轮 state 残留 |
| SQL 查询前去除可视化关键词 | 避免 SQL 生成模型被"画图"等词干扰 |
| BM25 用 child 文本检索 | child chunk 短文本关键词匹配效果优于长文本 |
| 对话上下文嵌入 system prompt | 避免 glm-4-flash 在多轮 chat messages 时跳出 JSON 输出模式 |
| paper_image 条件输出 | 仅当 chunk 含 table_title 时输出，避免空字段 |

## 6. 性能与资源

| 指标 | 数值 |
|------|------|
| 首次启动 | ~5s（无本地模型加载，仅初始化 BM25 索引） |
| 单次 SQL 查询 | ~2-3s（LLM 生成 + SQLite 执行），分解模式 ~8-12s |
| 单次 RAG 检索 | ~5-8s（双路召回 + 千帆 Rerank API + LLM 生成 + 溯源） |
| 可视化生成 | ~3-4s（LLM 解析 + matplotlib 渲染） |
| 复合问题（2-3 子任务） | ~10-15s |
| ChromaDB 向量库 | ~500MB（53716 child chunks，对应 11439 parent chunks） |
| SQLite 数据库 | 18MB |
| 内存占用（运行时） | ~200MB（无本地 embedding/reranker 模型，全部走千帆 API） |
| 向量库构建耗时 | ~32 分钟（千帆 Embedding API，16 条/批） |
